# Measurement Evaluation Report (Phase 10)

## 1. Dataset Provenance — READ THIS FIRST

**The 60 observations in `eval/synthetic_measurement_fixture.csv` (renamed in this review from the
misleading `tape_reference_measurements.csv`) are synthetic, hand-constructed test fixtures. They are
NOT physically tape-measured data from real human subjects.**

Evidence this is synthetic, not real-world measurement:
- Each of the 5 "subjects" has exactly one row per zone (60 = 5 subjects × 12 zones), with no repeat
  measurements, no measurement noise, and no missing/outlier data of the kind real tape measurement
  sessions produce.
- Within each zone, the `tape_cm` vs `estimated_cm` relationship is an almost constant percentage offset
  across all 5 subjects (e.g. chest is always ≈+3.3% higher than the estimate for every subject;
  waist is always ≈-2.9% lower). Real tape-measurement error against a photogrammetric estimate does
  not behave this way — it has subject-to-subject variance from posture, clothing, soft-tissue
  compression, and rater technique. A near-perfect constant bias per zone is the signature of data
  generated by applying a fixed multiplicative/additive formula, not independent physical measurements.
- There is no accompanying evidence (rater identity, measurement protocol, device, date, consent
  records) that these numbers were ever measured by a person with a tape on a real body.

**Conclusion: real-world measurement accuracy of the photogrammetric pipeline remains unvalidated.**
Everything below describes how the calibration math behaves on this synthetic fixture — it demonstrates
that the least-squares k-fitting code and evaluation harness work correctly, and nothing about accuracy
against real human bodies. Do not cite these MAE numbers as production accuracy claims.

## 2. Evaluation Methodology

The evaluation pipeline:
1. **Synthetic reference fixture**: `eval/synthetic_measurement_fixture.csv` — 60 rows, 5 synthetic subject
   profiles × 12 zones, each row an `(estimated_cm, tape_cm)` pair.
2. **Least-squares calibration (k-fitting)**: `eval/calibrate_k.py::fit_calibration_factors` solves the
   closed-form per-zone scale factor
   `k_zone = sum(tape_i * est_i) / sum(est_i^2)`, clamped to `[0.70, 1.30]`.
3. **Two reporting modes**, run by the same script:
   - **In-sample fit** (`fit_calibration_factors`): fits k on all 5 subjects and reports MAE on those
     same 5 subjects. This number is optimistic by construction — it is not a test of generalization.
   - **Leave-one-subject-out (LOSO)** (`leave_one_subject_out_eval`, added in this review): for each
     zone, fits k on 4 subjects and measures error on the 1 subject excluded from that fit, repeated
     once per subject. This is the only number in this report that reflects held-out performance.

### Exact commands

```bash
python -m eval.calibrate_k --input eval/synthetic_measurement_fixture.csv --output eval/calibration_factors.json
python -m pytest services/geometry/tests/test_measurements.py -q
```

The first command prints both the in-sample metrics and the LOSO metrics, and writes both into
`eval/calibration_factors.json` (keys `metrics` and `leave_one_subject_out`). The second runs the unit
tests covering `fit_calibration_factors` and `leave_one_subject_out_eval`, including a leakage check
that verifies a held-out subject's row never contaminates the k-fit used to score it.

### Zone mapping consistency

All 12 zone strings in the CSV (`chest`, `waist`, `hip`, `shoulder_width`, `sleeve_length`,
`torso_length`, `garment_length`, `inseam`, `thigh`, `neck`, `back_rise`, `upper_back`) match exactly
the `fitcore.schemas.MeasurementZone` enum values, and match the keys used in
`services/geometry/measurements.py::DEFAULT_CALIBRATION_FACTORS`. No zone is silently dropped or
mismatched between the CSV, calibration code, and measurement pipeline.

## 4. What this report does and does not demonstrate

**Demonstrates:**
- The least-squares k-fitting closed-form solution is implemented correctly and is numerically stable.
- The LOSO evaluation harness correctly excludes each held-out subject's rows from that fold's fit
  (verified by a unit test with an injected outlier subject, see
  `services/geometry/tests/test_measurements.py::test_leave_one_subject_out_eval_does_not_leak_held_out_subject_into_fit`).
- Zone identifiers are consistent end-to-end across the CSV, calibration code, and measurement pipeline.

**Does NOT demonstrate:**
- Real-world measurement accuracy of the photogrammetric pipeline against actual human bodies. **No
  physically tape-measured dataset currently exists in this repository.** Until one is collected (real
  subjects, a documented measurement protocol, and consent), any accuracy claim beyond "the calibration
  math works on a synthetic fixture" would be unsupported.
- Performance on clothing variation, uncontrolled camera distance/angle, or non-average body shapes —
  the synthetic fixture only covers 5 profile archetypes with no intra-subject variance.

### 6.2 Neck/waist/hip/thigh measurement fix — real-photo before/after

Raw photo-measurement stage (before SMPL fitting), real photos, height 165cm:

| Zone | Before (contaminated) | After (landmark-bounded) |
| :--- | :---: | :---: |
| Neck | 69.6 cm | **33.0 cm** |
| Waist | 104.6 cm | **77.7 cm** |
| Hip | 123.9 cm | **81.2 cm** |
| Thigh | 72.0 cm | **49.0 cm** |
| Chest (untouched control) | 111.9 cm | 111.9 cm (unchanged, as expected) |

The neck fix required two separate root causes, both confirmed by direct inspection of this subject's
real segmentation masks, not assumed:
1. **Front-view width**: the formulaic "neck row" landed inside the subject's hair, not the bare neck
   (visually confirmed: a crop of the real photo at that row showed clearly resolved individual hair
   strands, not skin). Fixed by bounding the row scan to an ear-span-derived window (ears are never
   narrower than the neck).
2. **Side-view depth**: even after fixing the front-view width, neck circumference stayed ~55cm because
   `_get_side_depth` was never bounded at all — hair draping past the head/neck in the profile silhouette
   inflated the depth component to 18.9cm (deeper than the neck was wide, anatomically implausible for
   a neck). Fixed by bounding the profile depth scan to a nose↔ear window per side view. This is the
   change that took the final neck measurement from 55.3cm to **33.0cm**.

Waist/hip/thigh were confirmed contaminated by a different mechanism: with this subject's arms hanging
naturally at her sides (a normal pose, not a framing defect), the hip-row scan line ran directly through
her hands in the segmentation mask (visually confirmed by overlaying the scan row on the real mask).
Fixed by bounding each scan to a landmark-derived window (hip-span for hip, shoulder→hip and hip→knee
linear taper for waist/thigh).

**Side-view depth for chest/waist/hip/thigh was checked and found NOT contaminated for this specific
photo set, and was deliberately left unbounded** — only neck depth showed the problem, so only neck
depth was changed. A different pose or photo set could behave differently; this was not re-verified
beyond the one subject tested.

### 6.3 What this does and does not demonstrate

**Demonstrates:** the specific, visually-confirmed contamination bugs above are fixed for this one real
photo set, with before/after numbers that moved from anatomically impossible (a 70cm neck, a hip
circumference measured hand-to-hand) to anatomically plausible for an adult human.

**Does NOT demonstrate:** real-world measurement accuracy. There is no tape measurement of this subject.
"Anatomically plausible" is a much weaker claim than "accurate" — a measurement can be perfectly
plausible and still be several centimeters wrong. The landmark-window margin factors
(`_FIXED_PAIR_MARGIN_FACTOR = 1.4`, `_TAPER_MARGIN_FACTOR = 1.2` in `measurements.py`) are anatomical
judgment calls validated against this one photo set, not tuned or validated against any ground truth.
A different body shape, pose, or framing could behave differently.

## 7. Synthetic SMPL Ground-Truth Round-Trip (Internal Consistency Only — NOT Real-Photo, NOT Tape-Measured)

`services/geometry/tests/test_synthetic_round_trip.py` (new) implements the round-trip described in the
original specification: start from a known SMPL mesh (known betas → known true measurements via
`MeshMeasurementExtractor`), render it to 4 synthetic orthogonal silhouettes and project its joints to
synthetic landmark positions using the exact same weak-perspective camera math already used by the
critic's overlay rendering, then run the **real** `calculate_photo_measurements` and `fit_smpl_shape` —
no MediaPipe, no mocked measurement logic — and compare the recovered chest/waist/hip/inseam against the
mesh's own ground truth, with a 1.5cm tolerance as specified.

**Result: FAILS, and is kept in the suite as `xfail(strict=True)` rather than hidden, weakened, or
deleted.** Even with a perfect, noise-free synthetic silhouette (no hair, no clothing, no occlusion —
conditions strictly better than any real photo), the round trip is off by:

| Zone | Error (run 1) | Error (run 2) |
| :--- | :---: | :---: |
| Chest | 17.5 cm | — |
| Waist | 10.8 cm | — |
| Hip | 26.8 cm | — |
| Inseam | 3.6 cm | — |

(Two parametrized body shapes were tested; both failed by a wide margin, well beyond the 1.5cm target.)

**Root cause (newly discovered this session, NOT fixed):** `measurements.py`'s photo-side method (2D
silhouette width/depth at a row chosen by percentage-of-torso-span heuristics, combined via a Ramanujan
ellipse approximation) and `fitting.py`'s `MeshMeasurementExtractor` mesh-side method (exact 3D
triangle-loop circumference at a *fixed* `y_plane` in SMPL's own local coordinate frame, e.g.
`waist_loop` at `y_plane=-0.05`) are two independently-built measurement techniques that were never
calibrated to find the *same* anatomical cross-section on the body. This is a deeper, architecture-level
mismatch than the hair/hand contamination bugs in §6 — fixing it would mean systematically reconciling
the row-selection heuristics in `measurements.py` against the fixed-plane definitions in `fitting.py`
(or vice versa), which was not attempted here because it is not a "smallest safe change": any fix risks
altering behavior already validated against the real photos in §6, and needs careful empirical
remapping across body shapes, not a quick numeric tweak.

This failure is also visible in the real-photo CLI run (§8): the fitted betas saturate at the ±4.0
clamp bounds on several components, the optimizer does not converge within 250 steps (final loss
178.8), and mean silhouette IoU is only ~0.43 — consistent with the optimizer being pulled toward
targets that don't correspond to geometrically achievable points on the actual mesh surface.

**What this does and does not demonstrate:** demonstrates that the photo- and mesh-side measurement
methods disagree systematically, independent of any photo-quality issue. Does NOT demonstrate anything
about real-world accuracy (there is no real body or tape measurement involved in this test at all — it
is pure internal self-consistency).

Known coverage limitation of this specific test: NOSE/EAR landmarks are not projected (no verified SMPL
vertex index for them was available), so the round trip only exercises the neck measurement's *fallback*
bound path, not the ear-span-bounded path a real photo with visible ears would use.

### Exact commands

```bash
python -m pytest services/geometry/tests/test_synthetic_round_trip.py -v
```

## 9. Remaining Limitations and Unverified Acceptance Criteria (2026-10 session)

- **No tape-measured ground truth exists anywhere in this repository**, for the synthetic fixture (§1–5,
  already labeled) or the real photos (§6). Every "plausible" or "improved" claim in this document is
  relative to anatomical expectation, not measured accuracy. This was true before this session and
  remains true after it.
- **The photo-side vs. mesh-side measurement-plane mismatch (§7) is unfixed, and it visibly affects the
  real photo's final result, not just the synthetic round trip.** Confirmed by re-running the real photo
  job after all §6 fixes: the raw photo-measurement neck is now correctly ~33cm (landmark-bounded,
  anatomically plausible), but the **final post-SMPL-fit neck value returned to the app is 54.9cm** —
  the SMPL fitting/critic stage pulls it back toward an implausible value because the mesh-side
  `neck_loop`'s fixed plane doesn't correspond to the same cross-section the now-fixed photo-side
  extraction targets. In other words: §6's fix is real and verified at the photo-measurement stage, but
  it does not fully propagate to the number a user actually sees for neck, because of this separate,
  unfixed issue. This does not block the demo (the pipeline still produces a plausible-looking twin end
  to end for most zones), but it means SMPL fitting loss/IoU for any real job is likely to stay mediocre
  (observed: final_iou ≈ 0.40–0.43, well below a well-converged fit) regardless of how clean the input
  photos are, and the neck zone specifically should not be trusted in the final displayed result until
  this is fixed.
- **Landmark-window margin factors (§6.3) are validated against exactly one real subject's photo set.**
  No claim is made about generalization to other body shapes, poses, or camera framings.
  `services/geometry/measurements.py` documents the factors and reasoning inline, but they are
  judgment calls, not fitted/tuned parameters.
  `services/geometry/measurements.py`'s `_FIXED_PAIR_MARGIN_FACTOR`/`_TAPER_MARGIN_FACTOR` constants are
  the exact values to revisit if more real photos become available.
  **No clamping or hardcoded expected measurement was added anywhere** — zones where the landmark bound
  can't be computed (e.g. ears/hips not detected) fall back to the pipeline's pre-existing anatomical-
  ratio fallbacks, and the one place a plausibility check exists (neck depth-vs-width ratio in
  `measurements.py`) only lowers reported *confidence*, never alters the reported *value*.
- **CLI runtime (§8) was not measured on 4-vCPU-constrained hardware**, only on a 12-core machine; the
  3-minute target is very likely met but not directly verified on target hardware.
- **4K/consistency test ("CLI and worker outputs are consistent where expected") was not independently
  re-verified this session** beyond confirming both code paths call the same underlying
  `calculate_photo_measurements`/`fit_smpl_shape`/`export_fit_result_to_glb` functions (the CLI path
  additionally skips the critic refinement loop entirely, by design — `"critic_refinement":
  "skipped_offline_mode"` in `measurements.json`).
- **Browser-rendered visual confirmation of `<model-viewer>` was not performed this session** (no browser
  automation tool was available) — the GLB bytes are confirmed valid and correctly served by the new
  `/api/twin/{id}/glb` endpoint, and the frontend TypeScript/build are confirmed clean, but no one has
  visually watched the 3D model actually render and rotate in a browser window this session.

## 10. Synthetic Round-Trip Follow-Up Investigation (2026-10 session) — root causes found via diagnostics, NOT assumption

§7 originally concluded the round-trip failure was a "photo-side vs. mesh-side measurement-plane
mismatch." That conclusion was **wrong, and was corrected this session** by tracing actual pixel/vertex
positions rather than theorizing. The real root causes, in descending order of impact:

### 10.1 Hip (and by extension waist/thigh, which share the same landmark machinery) — test-harness bug, not a production bug

The round-trip test's own synthetic "landmarks" were the bug. The test projected SMPL's **internal
skeletal joints** (e.g. joint 1/2, left_hip/right_hip — the kinematic hip-socket centers, used for
posing the skeleton) directly as stand-ins for MediaPipe landmarks. Diagnostic measurement showed these
two internal joints are only **~13.7cm apart**, close to the body's central axis — while the mesh's true
external hip silhouette is **~38.5cm wide**. A real pose detector (MediaPipe) estimates landmarks from
visual appearance, which sit near the visible body surface (the hip crease), not at the internal bone
center. Feeding the internal-joint positions into `measurements.py`'s (correctly designed) landmark-
bounded hip window made it clip the true width roughly in half (38.5cm → ~19cm) — a self-inflicted,
false failure.

**Fixed in the test only** (`test_synthetic_round_trip.py`): hip/knee landmarks now use the mesh's own
widest surface point at the joint's height, on the correct side — verified to reproduce the true
silhouette width within ~1cm (38.16cm vs. 38.46cm unbounded truth). Shoulder landmarks now reuse the
codebase's own pre-existing, verified acromion surface vertices
(`MeshMeasurementExtractor.idx_l_acromion` / `idx_r_acromion`). **No production code changed for this
part** — `measurements.py`'s landmark-bounded hip/waist/thigh windows (§6) were already correct; they
were being fed unrealistic input by the test.

### 10.2 Inseam — a real, confirmed production bug, now fixed

`fitting.py`'s `MeshMeasurementExtractor.extract_measurements()` computed inseam as
`joints[0, 1] - joints[7, 1]` (pelvis joint to ankle joint), despite its own code comment already saying
*"crotch level down to left ankle"*. Diagnostic comparison: the pelvis joint is ~9.5cm above the hip
joints and ~18.8cm above the mesh's own `idx_crotch` vertex (already defined in the same file, currently
used for `back_rise`, never for inseam). The photo-side's independently-derived crotch estimate (hip
landmark + 12% of leg span) agreed with `idx_crotch` to within **~0.9cm**, and disagreed with the pelvis
joint by **~19.7cm**. This is clear evidence the pelvis joint was simply the wrong reference point.

**Fixed in production** (`services/geometry/fitting.py`): inseam now computes
`vertices[self.idx_crotch, 1] - joints[7, 1]`. This also corrects the live SMPL-fitting loss term for
inseam on every real job, not just the test.

### 10.3 Chest — a real, confirmed production bug, partially fixed, genuine limitation remains

`measurements.py`'s chest width scan was **completely unbounded** (unlike waist/hip/thigh, which already
had landmark bounds from §6). Diagnostic: at the formulaic chest row ("immediately below the armpit"),
raw unbounded width on the synthetic mesh was 66.5cm for a mesh whose true chest circumference is
88.2cm total (width alone should be well under 40cm). The same pattern was confirmed on the **real
photo**: unbounded chest width 43.5cm, chest circumference reported as 111.9cm throughout the prior
session — a value that was never independently sanity-checked before this investigation and is likely
still somewhat inflated.

**Fixed in production** (`services/geometry/measurements.py`): added the same shoulder→hip taper bound
already used for waist. Real-photo effect: chest width 43.5cm → 35.4cm, total chest circumference
111.9cm → 98.0cm — a real, meaningful improvement, re-verified against the live pipeline.

**Not fully fixed — genuine, diagnosed limitation.** On the synthetic mesh, the bound only reduced chest
width from 66.5cm to 51.1cm, nowhere near the true ~30cm. Tested arm-abduction angles from 45° (SMPL's
own canonical pose) up to 110° (unrealistically wide): the arm and torso remain part of the **same
contiguous region** in the 2D silhouette at every angle tested — there is no background-color gap for
any landmark-derived column window to find, because the shoulder/deltoid region is anatomically
continuous with the upper arm in a flat silhouette projection. This is a genuine 2D-silhouette ambiguity,
not a fixable bounding-window bug. A bounded implementation plan (morphological gap detection to
suppress `cv2.fillPoly` rasterization noise; a directed shoulder→elbow exclusion line instead of a
static window; or tightening the photo-capture validator's posture requirement) is documented in
`test_synthetic_round_trip.py`'s module docstring but was **not implemented** — it needs validation
against more real photos than the one set available this session, per the exact lesson learned in §10.1.
